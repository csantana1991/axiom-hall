Name the idea as a bug in the measurement, not as a mystery in the ring. A full ring is a failed push. The naive listing pushes in a loop and never pops. After capacity successful writes, every push returns false, and a loop written as while not push spins. The benchmark times a livelock. Report that as a bug in the measurement, which is what it is. A spinning benchmark reports infinity or nonsense.

Use the capacity-four ring you can already walk, so the failure has a count. Four pushes succeed. The monotonic head is four, the tail is still zero, and the fifth push sees a negative difference on slot zero. It returns false. Nothing in that false mutated the ring. A correct caller treats false as "not now" and either pops, or backs off, or counts a drop. The naive listing does none of those. It stays in the timed region and tries the push again. The fifth attempt fails, the sixth fails, and the attempts do not end. The timer is measuring a thread that will not complete the unit of work the benchmark thinks it is measuring. If the harness waits forever, you have no sample. If the harness eventually gives up, the number you get is the harness's patience, not a handoff.

Say what a livelock is, in this narrow setting, so the word does not float in from a different course and change the claim. Both logical conditions of the protocol are well defined. The producer is correctly observing a full ring. The consumer is absent, so the ticket the producer needs will never be published. No deadlock of two locks has occurred, because this design was not taking a lock. Progress on the handoff will also never occur, because the only thread inside the timed region is the one that cannot proceed, and it is not doing the pop that would make progress possible. The loop is busy. The transfer is stuck. Timing that busy loop and calling the result a latency is the measurement bug.

A second capacity makes the same point without new ideas. On the sixteen-slot ring, sixteen pushes succeed and the seventeenth returns false. If the timed loop is "push the next identifier" with no consumer, the timer includes sixteen real writes and then an unbounded run of failures. Sixteen divided by sixteen plus a huge number of failed attempts goes to zero. Almost none of the timed attempts are handoffs. If the benchmark counts every attempt as an operation, the operations per second climb with how fast you can fail a compare against a ticket that does not match. That climb is not throughput of events. It is throughput of refusals. The slide states the symptom plainly. A spinning benchmark reports infinity or nonsense. Infinity is what a rate becomes if you are willing to count empty iterations and the denominator of "time per successful handoff" has no successes after the fill. Nonsense is the rest: a finite number that is mostly the cost of a failed push, labeled as if it were the cost of a successful one.

The checksum is the instrument that should have been running instead, and it will not save a push-only loop by itself. The default main pushes order identifiers zero through N minus one and the consumer sums them. The sum is N times the quantity N minus one, divided by two. For one hundred thousand events, that sum is four billion nine hundred ninety-nine million nine hundred fifty thousand. The consumer has to be alive for the sum to exist. A push-only loop never constructs the sum, because nobody is on the other side adding. If you disable the consumer and then look for a latency, you have also disabled the only correctness check the default build was willing to give you. Run the checksum before you believe a nanosecond. A push-only timing has no checksum to run.

You can see the nonsense as a fraction without pretending to have timed anything. Let the capacity be four. Let a harness run for long enough that the producer completes four successful pushes and then one thousand failed pushes before somebody stops it. The successes are four out of one thousand four attempts, which is one part in two hundred fifty-one. If each attempt, success or failure, were mistakenly counted as an event, the reported event count would be about two hundred fifty-one times the number of real handoffs. A rate built on that count is two hundred fifty-one times too eager, and the factor grows if the harness is allowed to fail more times. Nothing in the protocol changed between the thousandth failure and the first. The ticket was still the first publish, sequence one, against head four. The measurement changed only by lasting longer. A number that improves when you spin longer is not a latency of a transfer. It is a latency of a branch that already knows the answer.

The checksum formula makes the missing consumer obvious on a tiny N as well. For N equal to four the honest sum is six, but only if a consumer received zero, one, two, and three. In the push-only listing nobody receives them. There is no sum to compare with six. Inventing a latency in that silence is the same move as inventing a sum. You would be reporting a property of a run that never closed the equality. The default build exists so the equality can close, on one hundred thousand events, at four billion nine hundred ninety-nine million nine hundred fifty thousand. A benchmark that cannot close it is not a faster version of the default build. It is a different, broken experiment.

The question to answer is whether the spin is acceptable if you count only the successful pushes and ignore the failures that follow. It is not, once the successes stop. The successful prefix has length equal to the capacity, and then the clock is still running while nothing succeeds. Any average that divides a fixed number of successes by a time that includes the subsequent spin will fall toward zero events per second as the spin lengthens, or it will be cut off at an arbitrary timeout. Either result is a property of the timeout and the capacity, not of a steady handoff. Capacity four with a one-second spin after the fill is a benchmark of "four events, then waiting." You can report that sentence. You cannot divide four by the second and call the quotient a sustained rate of the engine, unless you also say that the engine spent almost the entire second refusing. The honest name for the refusal is a failed push on a full ring.

What the claim does not mean is that returning false is a defect in the protocol. False on a negative difference is the protocol telling the truth. The defect is a measurement that never pops, then times the consequence, then publishes the consequence as a performance of the handoff. The claim also does not mean that a full ring should block inside push until space appears. This listing returns false. A blocking push would be a different function, and a benchmark of it would be a benchmark of waiting for a consumer, which only makes sense if the consumer exists. In the naive listing the consumer does not exist. You would be timing a wait for an event that nobody will cause. Report the bug in the measurement. Then change the measurement, which is the next part of the hour, rather than changing the word false into a retry you do not admit.

The repair is pairing. Threads must be paired. Google Benchmark can run the same function on two threads. Thread zero pushes once per iteration. Thread one pops once. Iterations match, so the ring does not fill, aside from startup jitter. Use real time is appropriate because each thread waits on the other. One iteration is one push and one pop, on two threads. Yield on failure so a debugger can breathe. Checksum the payload in a separate build. Timing is not a proof.

Walk the paired iteration on the capacity-four ring with no jitter first, so the ideal case is obvious. Start empty, tickets zero, one, two, three, head zero, tail zero. Iteration zero: the producer pushes once, head becomes one, slot zero publishes sequence one. The consumer pops once, reads that payload, tail becomes one, slot zero publishes four. The ring is empty again. Iteration one does the same on slot one. Each iteration adds one to the head and one to the tail. The occupancy returns to zero before the next iteration if the two sides stay in lockstep. The ring does not fill. Four slots are plenty, because you never hold more than one event, and you hold it only between the push and the matching pop. The timed work is a handoff, not a refusal.

Startup jitter is the aside, and it needs a number so it does not become a shrug. Suppose the producer runs twice before the consumer runs at all. After two pushes, head is two, tail is zero, occupancy is two. Capacity four can absorb that. The consumer then pops once, occupancy falls to one, and if the iteration counts are required to match, the consumer still owes one pop. When the counts catch up, occupancy returns to zero. The ring did not fill. Now suppose the scheduler lets the producer run four times before the consumer starts. Occupancy reaches four. The next producer attempt returns false. That is still the full-ring test, and it can happen at startup even in a paired benchmark, because "iterations match" is a statement about the completed counts, not a lock that forces the two threads to alternate instruction by instruction. The aside matters. You do not pretend jitter is impossible. You notice that a head start smaller than the capacity is absorbed, and a head start of a full capacity produces a failed push that must not be spun into a livelock.

Yield on failure is the practical distinction between a bug and a pause a debugger can survive. If the producer sees false because it ran ahead by a full capacity, and it yields, it gives the consumer a chance to be scheduled and to publish tail plus capacity. The failed push stays a failed push. The thread stops burning the core for a moment. A debugger can break in. A while-not-push loop that does not yield, on a full ring with a stalled consumer, is the livelock again. Yield is not a proof that the event was delivered. It is a way to fail without hiding the machine from the person trying to see why. If the consumer never runs, the yields continue, and you still do not have a latency. You have a polite spin. Report it as a consumer that did not arrive, not as a nanosecond.

Use real time, rather than a per-thread processor timer, because each thread waits on the other. Suppose the producer pushes and then, on this iteration, has to wait while the consumer is slow to pop. A processor timer that pauses whenever the producer is not on-CPU will omit the wait. The handoff, as a wall-clock fact, included the wait. The two threads' processor times might each look like a few instructions, while the event's travel from push to pop took much longer because one side was late. Use real time is appropriate for that reason. It does not, by itself, produce a hardware latency you can paste onto the ambition of two hundred fifty nanoseconds. It produces a wall-clock reading of a paired iteration, on whatever machine, flags, and pin you still have to write down. Compiler, flags, CPU, pin. Capacity, event size, cold or warm. Percentile, not only the mean, once you are on metal. A mean hides the iteration where the jitter filled the ring and the yield had to fire. A percentile is how you admit that iteration exists.

Keep the checksum in a separate build, on purpose. Timing is not a proof. The proof you have today is the sum. For N equal to one hundred thousand, the consumer must report four billion nine hundred ninety-nine million nine hundred fifty thousand, which is one hundred thousand times ninety-nine thousand nine hundred ninety-nine, divided by two. A torn or dropped event fails the equality. The benchmark build, with the define AXIOM WITH BENCHMARK and the benchmark library linked, is allowed to focus on the paired push and pop. It is not allowed to replace the checksum. If you only have a timing binary, and you have never seen the sum, you do not yet know that the bytes which arrived were the bytes which were sent. Run the default threaded checksum of one hundred thousand events first. If it mismatches, stop. Do not interpret a timing of a broken ring.

Put the jitter in units of slots so the capacity is doing arithmetic and not acting as a vibe. Capacity four absorbs a producer head start of one, two, or three successful pushes. Occupancy one, two, or three is not full, and the next push still finds a ticket that matches. A head start of four fills the ring. The fifth attempt is the first false return. Capacity sixteen absorbs fifteen unmatched pushes and refuses the sixteenth. The paired design does not promise that the scheduler's head start is smaller than the capacity. It promises that the iteration counts are the same length, so a head start is a transient bulge rather than a trend that adds one extra unmatched push on every iteration forever. A bulge of four on a capacity of four is already a refusal. A bulge of four on a capacity of sixteen is occupancy four, head minus tail equal to four, and the next push still succeeds. Yield on that success is unnecessary. Yield on the refusal is the debugger's breath. If you yield on every success as well, you have changed the timing, and you should say so, because a voluntary yield on the fast path is part of the number. The lecture asks for a yield on failure, not for a yield on every iteration. Those are different programs.

Use real time has a small numerical sketch that keeps the definition honest. Suppose one paired iteration takes one thousand nanoseconds of wall time, and each thread is actually executing for two hundred of those nanoseconds, with the rest spent waiting on the other side. Those durations are a sketch of the gap, not a measurement. A processor timer might report something near two hundred nanoseconds per thread. The wall clock reports one thousand. The handoff the other thread experienced was the thousand, because that is how long the event took to be pushed and popped in the world. Use real time selects the thousand. It still does not select two hundred fifty, and it still does not run on the browser. If your real iteration is slower or faster, you write the number the counter gave you, next to the CPU, the flags, and the pin, or you write nothing.

The question to answer is why the iteration count has to match, rather than letting the consumer pop as fast as it can in an unstructured second thread. Unstructured popping can be correct and still be a bad measurement. If the consumer is faster and blocks inside a pop you redefined to wait, you are timing the wait. If the consumer is slower and the producer pushes without a bound, the ring fills and you are back to timing false returns. Matching the iterations, one push and one pop, keeps the occupancy from trending upward with the sample. It does not remove startup jitter, which is why the lecture says "aside from startup jitter" instead of "the ring never observes a full slot." The match is a design of the experiment. It is not a property the ring enforces for you.

What the claim does not mean is that a paired Google Benchmark run is automatically a sub-two-hundred-fifty-nanosecond result, or that use-real-time converts JavaScript into metal. The pairing fixes the push-only bug. It does not grant the hypothesis. You still need the CPU, the flags, and the pin, and you still need a counter rather than a browser. The claim also does not mean that a failed push during startup jitter is a protocol failure. It is the full test working, during a head start the capacity could not absorb. Yield, let the pop happen, and keep the sample only if you understand which attempts were refusals. If you cannot say whether a given iteration pushed successfully, you do not yet have a latency sample. You have a mixture, and a mixture is not a mean you may publish as the handoff.

The last idea of the hour is about the instrument in front of you. JavaScript is a different instrument. The lab's burst mode runs the protocol on one thread and counts drops when the producer outruns the consumer. Run the burst with pressure above one and watch the drops. That is the push-only bug, slowed down. Then set the pressure to one and read a JavaScript rate that you will not call a hardware latency.

One thread cannot be the paired experiment, and the lab does not pretend to be. Burst mode interleaves the protocol on a single thread and, when the pressure is above one, lets the producer outrun the consumer. The lab brief does not ask you to treat a particular pressure reading as a calibrated ratio from a paper. It asks you to raise the pressure above one and watch the drops, then to set it to one. Above one, the producer gets ahead, the ring fills, further pushes return false, and the lab counts those drops. The drops are the failed pushes. You are watching the naive benchmark in slow motion, with a counter of refusals instead of a timer wrapped around an infinite spin. A producer that is not matched by a consumer does not have a throughput. It has a growing list of events that never entered.

Pressure one is the other setting, and it is the closest the single thread comes to the paired iteration. The producer does not outrun the consumer. Occupancy does not trend to the capacity from the pressure itself. You may then read a rate, in operations per second, of that JavaScript loop. The rate is real for the loop. It includes whatever the browser does between the steps. It is irrelevant to the C plus plus target. The target was a hypothesis about pinned metal, a warm cache, and the binary you compile with optimization level three, the C plus plus twenty standard, and pthread. The lab was never that binary. Print both sentences if you show the number. Sentence one: this is how fast the JavaScript loop ran. Sentence two: this is not a hardware latency and not the C plus plus handoff. One sentence without the other is how a browser number becomes a fabricated nanosecond. Dividing one billion by the JavaScript rate yields a quotient in nanoseconds that still belongs to the browser. You may not move the quotient onto the metal slide.

Connect the drop count to the checksum so the burst cannot be shrugged off as a display detail. The formula for a complete run still stands. The sum of identifiers zero through N minus one is N times the quantity N minus one, divided by two. For eight identifiers and no drops, that sum is twenty-eight. If the burst dropped two of them, the consumer's sum is the sum of the six that entered, and comparing that short sum with twenty-eight fails the equality. The failure is what the checksum is for. A drop is a push that returned false. The event stayed out. It is not, by itself, a torn cell. You will separate tear from drop in the defense. Here, you respect the drops the burst shows when the pressure is above one, and you do not relabel them as throughput. The lab is not being assigned a specific drop total here, because a single thread can interleave the steps in more than one legal order. The brief's demand is directional. Pressure above one produces drops you can watch. Pressure one does not ask you to call the resulting rate a hardware latency.

A pressure of one can still drop if the single thread clumps pushes by accident, and you should not be surprised into relabeling the rate. The brief's contrast is directional rather than a promise that pressure one is a mathematical proof of zero drops. If you see drops at pressure one, say that you see them, and do not call the rate a clean handoff rate. If you see no drops, the rate is still a JavaScript rate. Either way you print both sentences before the number leaves your mouth. The C plus plus side of the comparison remains the paired benchmark, two threads, one push and one pop per iteration, checksum living in the other build. Nothing you toggle in the browser edits that file. A result has a counter. An ambition has a sentence. The lab has a third thing, an instrument reading, and it stays in its own column.

The question to answer is whether a JavaScript rate at pressure one, if it looks very fast, could at least be a lower bound on the C plus plus rate. It could not, not as a claim you are allowed to make. A lower bound is a theorem about the same program or a proved relation between two programs. These are different languages, different runtimes, and different schedulers. The JavaScript loop can be slower than the binary, and a particular browser moment can also be unrepresentative in either direction relative to a machine you have not pinned. The lecture does not give you an inequality. It gives you two sentences. The operations per second are real for that JavaScript loop and irrelevant to the C plus plus target. Relevance would require the C plus plus measurement. Until you have it, the JavaScript rate does not bound it, does not estimate it, and does not replace it.

What the claim does not mean is that the lab is useless, or that pressure one is a cheat. The lab is how you see drops when the producer outruns the consumer, which is the push-only bug slowed down until a person can watch it. Pressure one is how you see the protocol move without that particular bug, and the rate you read there is still labeled as JavaScript. The claim also does not mean you should hide the browser number from the defense. You may show it. You must print both sentences.
