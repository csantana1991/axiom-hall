Three orders cover this protocol. You do not need a fourth word to publish a payload through the ring. Relaxed is enough for a counter that only one thread writes, when no payload depends on that counter. Acquire on a load pairs with release on a store. If you see the release, you see the writes that happened before it in that thread. The payload store happens before the sequence release. The consumer’s acquire of the sequence happens before the payload read. That pairing is the whole publication story. The reference you trust for the orders is the language reference, not these lecture notes. The notes are placement. The reference is the definition.

Say the placement as a sequence of actions you could point at in the listing. The producer writes the data. Then it release-stores the sequence ticket, and the value it stores is head plus one. The consumer acquire-loads that sequence. If the load observes the stored ticket, the consumer then reads the data. Writes that happened before the release, in the producer’s thread, become visible to the consumer after the acquire. A release store synchronizes with an acquire load that reads the value it stored. That sentence is the one the notes tell you to keep. Everything else is where you put the two operations.

Put numbers under the sentence so it cannot stay a slogan. Let head be five. The producer writes the payload for that ticket, then release-stores the sequence as head plus one. Five plus one is six. The ticket value six is what the release publishes. Suppose the consumer’s tail is also five. The consumer is allowed to read when the sequence has reached tail plus one. That sum is six as well. If the acquire load returns six, the ticket has arrived, and the payload writes that preceded the release are visible to this consumer. If the acquire load returns five, the sequence has not reached six. The slide’s empty test is exactly that: the sequence has not reached tail plus one, so the consumer treats the slot as empty. The difference is five minus six, which is negative one. A negative difference means the ticket is not yours yet. You do not read the payload on a negative difference. The order pair never got a chance to fire, because the acquire did not observe the release’s value.

Now the producer’s mirror of the same test. The slide says that on the producer side, full means the sequence is still behind head. Let the sequence sitting in the cell be four, and let head be five. Four is behind five. The difference, sequence minus head, is negative one, which is less than zero, so the ticket is not yours yet and the producer must not overwrite the cell. Full and empty can both be a negative difference. They are negative against different references: head for the producer, tail plus one for the consumer. The order words do not decide which reference. The protocol does. Relaxed, acquire, and release decide what else becomes visible once a test has passed.

Change one input. Move head from five to eight, and recompute the release and the empty test. The release store publishes head plus one, which is nine. If the consumer’s tail is eight, tail plus one is nine, so an acquire that returns nine may proceed to the payload, and an acquire that returns eight may not. Eight minus nine is negative one, still not yours. If instead the cell’s sequence is seven while head is eight, the producer sees seven behind eight, difference negative one, and the cell is full. The arithmetic shifted by three because head shifted by three. The shape of the tests did not change, and the placement of the orders did not change. Payload store, then release of the new ticket, then, on the other side, acquire of that ticket, then payload read.

You might ask why the compare-and-swap on head is relaxed, if publication is so delicate. Because the ticket, not the counter, publishes the data. The slide says this directly. The counter head is a value only one side updates in the single-producer case, and no payload rides on that counter’s store. Relaxed is the order the lecture assigns to that situation. The release is on the sequence store that happens after the payload write. If you moved the release onto head and left the sequence relaxed, you would be publishing a different variable from the one the consumer acquires. The consumer is told to acquire the sequence. A release the consumer never acquires does not bring the payload across. Placement is the design. The relaxed counter is relaxed on purpose.

The weak compare-and-exchange is why the loop exists. The slide names spurious failure as the reason. The operation is allowed to fail even when you might have expected it to succeed, so a single attempt is not a protocol. The loop retries. One producer could skip the compare-and-swap entirely, because a single writer does not need to race itself for head. The listed code keeps the compare-and-swap so the protocol stays obvious. Keeping it is a teaching choice about the listing, not a claim that the single producer is logically required to fail and retry. If you delete it, you must still publish with the release on the sequence after the payload store. If you keep it, the loop stays, and the order on that compare-and-swap stays relaxed.

What these three orders do not mean is that every atomic in the program becomes correct once the words appear somewhere. Relaxed on the publishing store would drop the pairing. Acquire on a load that reads the wrong variable would pair with nothing. Release of sequence equal to head plus one, with the payload write still in the future, would publish a ticket for data you have not stored. The formula is an order of actions, not a set of decorations. What they also do not mean is that the notes have replaced the language reference. The notes say the reference is the source and the lecture notes are not. You use the notes to remember placement: write data, release the sequence as head plus one, acquire the sequence, read data. You use the reference when you need the definition of synchronizes-with, not a paraphrase from a classroom.

Walk one consumer step that fails and one that succeeds, with tail held at five and the released value at six, so success and failure are adjacent integers. Failure: the acquire observes five. Tail plus one is six. Five has not reached six. Difference negative one. The consumer does not read the payload. There is no claim, on this attempt, that any particular producer write is visible, because the acquire did not observe the release. Success: a later acquire observes six. The load read the value the release stored. Writes before that release, in the producer thread, are visible after this acquire. The consumer may read the payload, and it must do that read after the successful acquire, not before. Reordering the read upward, ahead of the acquire, would look at the payload without the pairing the protocol relies on. The order is a constraint on your code, not a mood you add in a comment.
