A linear hash, of the modest kind this lab is pointing at, sends a key to a column by a multiply, an add, and a remainder modulo the width. It is not a cryptographic construction, and you should not talk about it as if it were one. Take width four, the picture width, and number the eight roots from zero through seven so the arithmetic is visible. Let the first row send key x to x modulo four. Zero and four land in column zero. One and five land in column one. Two and six land in column two. Three and seven land in column three. Four pairs, forced by eight keys and four columns. Let the second row send x to three x plus one, modulo four. Key zero goes to one. Key one goes to zero, because three plus one is four, and four modulo four is zero. Key two goes to three, because six plus one is seven, and seven modulo four is three. Key three goes to two, because nine plus one is ten, and ten modulo four is two. Key four goes to one, the same column as key zero. Key five goes to zero, the same column as key one. Key six goes to three, with key two. Key seven goes to two, with key three. So this second row collides in the same pairs the first row did. Two rows, and this particular choice of linear maps did not separate zero from four. The minimum will not be rescued for that pair, and that is a legal outcome of a tiny hash, not a bug in the minimum.

Stream five arrivals of key zero and three arrivals of key four, the pair that collides in both rows. Every arrival of either key increments row zero’s column zero, and every arrival increments row one’s column one. Both cells read eight. The query for key zero takes the minimum of eight and eight, which is eight. Key zero really arrived five times. Eight is an overestimate by three, which is exactly key four’s count, because every one of key four’s arrivals landed in both of key zero’s cells. The query for key four also returns eight, against a truth of three. Both estimates sit above their truths. The sketch is one-sided and, on this hash, not tight. You do not repair it by switching to a cryptographic name while keeping width four. Eight keys into four columns collide by the pigeonhole principle, cryptographic or not. A family can randomize which pairs collide. It cannot give eight keys eight private columns inside a width of four.

Change one input. Keep the two linear maps and the width, and replace key four’s three arrivals with three arrivals of key one. Key zero and key one do not share a column in row zero: zero goes to column zero, one goes to column one. They do not share a column in row one either: zero goes to column one, one goes to column zero. Five arrivals of key zero leave five in row zero column zero, and five in row one column one. Three arrivals of key one leave three in the other cell of each row. The minimum for key zero is the minimum of five and five, which is five. The minimum for key one is three. The same style of hash, the same width, a different partner, and the estimate meets the truth because the partner missed both cells. Collisions are the point, including the collisions that do not happen to hit the key you queried. A demonstration in which every pair misses is the costume. This pair missed. The earlier pair, zero and four, did not. You want a lab in which both kinds can occur.

Add one arrival of key four on top of the clean picture, so a single colliding update has a visible cost. Before that arrival, key zero’s estimate is five. Key four maps to the same cells as key zero in both rows. One arrival adds one to each of those cells. They read six and six. The minimum becomes six. The truth of key zero is still five. The overestimate is one, equal to the number of colliding arrivals that hit every row’s cell. If a third row used a different linear map that sent key four somewhere else, that third row’s cell would still read five, and the minimum would return to five. The depth would have bought a clean look. The two-row toy did not have that third map. You can see the purchase in one extra row without pretending two-by-four has become a calibrated epsilon.

You might ask whether you should replace the linear maps with a cryptographic hash so the eight roots stop colliding and the estimate stops printing eight. On width four, they will not stop. There is nowhere to put eight private columns. On a width large enough to hold them, for example the width twenty-eight you sized for epsilon one tenth, a hash that sends all eight roots to different columns never collides on this toy. The lecture’s sentence still applies. That hash is a lookup table in a costume, relative to an alphabet of eight. The estimate will match the truth because you built a direct address table for a tiny alphabet, which you were already allowed to do honestly by keeping eight counters and calling it a histogram. The costume is claiming you tested the sketch. You tested the case the analysis does not worry about. The algorithm does not get easier when the alphabet grows past the width. Your audit gets harder, because you can no longer see every collision by eye. A cryptographic family is about how you model the hashes in a proof, not about a permission slip to skip collisions on the demo. The lab’s choice of tiny linear hashes is so the collision stays arithmetic, like three x plus one modulo four, rather than a digest you cannot redo on paper.

What “collisions are the point” does not mean is that a broken hash is a virtue, or that any map modulo w will do in a real deployment of the sized bound. The bound, width the ceiling of e over epsilon and depth the ceiling of the natural log of one over delta, is a statement about hashes that behave well enough for the analysis, not about the first linear coefficients you wrote down. The two maps above failed to separate zero from four in either row. A sized sketch with a bad family can miss its delta. The lab is allowed to use tiny maps because it is not cashing epsilon. You are not allowed to cite the lab’s maps as the family in the theorem. What the costume sentence also does not mean is that every collision-free run on eight keys is dishonest storage. If you meant to store eight counters, say so. Exact histograms are allowed when the alphabet is tiny. The dishonest move is to store them and call the result evidence about a count-min bound.
