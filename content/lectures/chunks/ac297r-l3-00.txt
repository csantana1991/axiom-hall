Name the idea as a bug in the measurement, not as a mystery in the ring. A full ring is a failed push. The naive listing pushes in a loop and never pops. After capacity successful writes, every push returns false, and a loop written as while not push spins. The benchmark times a livelock. Report that as a bug in the measurement, which is what it is. A spinning benchmark reports infinity or nonsense.

Use the capacity-four ring you can already walk, so the failure has a count. Four pushes succeed. The monotonic head is four, the tail is still zero, and the fifth push sees a negative difference on slot zero. It returns false. Nothing in that false mutated the ring. A correct caller treats false as "not now" and either pops, or backs off, or counts a drop. The naive listing does none of those. It stays in the timed region and tries the push again. The fifth attempt fails, the sixth fails, and the attempts do not end. The timer is measuring a thread that will not complete the unit of work the benchmark thinks it is measuring. If the harness waits forever, you have no sample. If the harness eventually gives up, the number you get is the harness's patience, not a handoff.

Say what a livelock is, in this narrow setting, so the word does not float in from a different course and change the claim. Both logical conditions of the protocol are well defined. The producer is correctly observing a full ring. The consumer is absent, so the ticket the producer needs will never be published. No deadlock of two locks has occurred, because this design was not taking a lock. Progress on the handoff will also never occur, because the only thread inside the timed region is the one that cannot proceed, and it is not doing the pop that would make progress possible. The loop is busy. The transfer is stuck. Timing that busy loop and calling the result a latency is the measurement bug.

A second capacity makes the same point without new ideas. On the sixteen-slot ring, sixteen pushes succeed and the seventeenth returns false. If the timed loop is "push the next identifier" with no consumer, the timer includes sixteen real writes and then an unbounded run of failures. Sixteen divided by sixteen plus a huge number of failed attempts goes to zero. Almost none of the timed attempts are handoffs. If the benchmark counts every attempt as an operation, the operations per second climb with how fast you can fail a compare against a ticket that does not match. That climb is not throughput of events. It is throughput of refusals. The slide states the symptom plainly. A spinning benchmark reports infinity or nonsense. Infinity is what a rate becomes if you are willing to count empty iterations and the denominator of "time per successful handoff" has no successes after the fill. Nonsense is the rest: a finite number that is mostly the cost of a failed push, labeled as if it were the cost of a successful one.

The checksum is the instrument that should have been running instead, and it will not save a push-only loop by itself. The default main pushes order identifiers zero through N minus one and the consumer sums them. The sum is N times the quantity N minus one, divided by two. For one hundred thousand events, that sum is four billion nine hundred ninety-nine million nine hundred fifty thousand. The consumer has to be alive for the sum to exist. A push-only loop never constructs the sum, because nobody is on the other side adding. If you disable the consumer and then look for a latency, you have also disabled the only correctness check the default build was willing to give you. Run the checksum before you believe a nanosecond. A push-only timing has no checksum to run.

You can see the nonsense as a fraction without pretending to have timed anything. Let the capacity be four. Let a harness run for long enough that the producer completes four successful pushes and then one thousand failed pushes before somebody stops it. The successes are four out of one thousand four attempts, which is one part in two hundred fifty-one. If each attempt, success or failure, were mistakenly counted as an event, the reported event count would be about two hundred fifty-one times the number of real handoffs. A rate built on that count is two hundred fifty-one times too eager, and the factor grows if the harness is allowed to fail more times. Nothing in the protocol changed between the thousandth failure and the first. The ticket was still the first publish, sequence one, against head four. The measurement changed only by lasting longer. A number that improves when you spin longer is not a latency of a transfer. It is a latency of a branch that already knows the answer.

The checksum formula makes the missing consumer obvious on a tiny N as well. For N equal to four the honest sum is six, but only if a consumer received zero, one, two, and three. In the push-only listing nobody receives them. There is no sum to compare with six. Inventing a latency in that silence is the same move as inventing a sum. You would be reporting a property of a run that never closed the equality. The default build exists so the equality can close, on one hundred thousand events, at four billion nine hundred ninety-nine million nine hundred fifty thousand. A benchmark that cannot close it is not a faster version of the default build. It is a different, broken experiment.

The question to answer is whether the spin is acceptable if you count only the successful pushes and ignore the failures that follow. It is not, once the successes stop. The successful prefix has length equal to the capacity, and then the clock is still running while nothing succeeds. Any average that divides a fixed number of successes by a time that includes the subsequent spin will fall toward zero events per second as the spin lengthens, or it will be cut off at an arbitrary timeout. Either result is a property of the timeout and the capacity, not of a steady handoff. Capacity four with a one-second spin after the fill is a benchmark of "four events, then waiting." You can report that sentence. You cannot divide four by the second and call the quotient a sustained rate of the engine, unless you also say that the engine spent almost the entire second refusing. The honest name for the refusal is a failed push on a full ring.

What the claim does not mean is that returning false is a defect in the protocol. False on a negative difference is the protocol telling the truth. The defect is a measurement that never pops, then times the consequence, then publishes the consequence as a performance of the handoff. The claim also does not mean that a full ring should block inside push until space appears. This listing returns false. A blocking push would be a different function, and a benchmark of it would be a benchmark of waiting for a consumer, which only makes sense if the consumer exists. In the naive listing the consumer does not exist. You would be timing a wait for an event that nobody will cause. Report the bug in the measurement. Then change the measurement, which is the next part of the hour, rather than changing the word false into a retry you do not admit.
