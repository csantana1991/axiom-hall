Price is the field the note singles out. Price is a double in the teaching file so the benchmark matches the earlier listing. A double price, with an implicit tick, will eventually compare unequal to itself. That is the same identity failure the book lecture named for ticks, and here it is a schema failure. If you promote the struct to production, change price to an integer tick and update the checksum test. The note does not give you the new checksum value. You update the test because the bytes changed, not because you remember a magic number. Integer tick means equality is integer equality. Two events at the same tick compare equal on price. The teaching double is allowed only inside the teaching file, for the reason the note gives: the benchmark matches the earlier listing. It is not a permission slip for production.

A schema version is what keeps a replay from lying when those bytes change. Suppose the old layout and the new layout differ by the price representation, double versus integer tick. A replay that reads old bytes with the new struct will interpret the old price bits as an integer, or it will read off the end of a field into the next field. The timestamp, the order id, the quantity, and the side can all shift relative to the truth. The log will happily return those bytes. The lie is in the interpretation. A version on the layout tells the reader which interpretation is legal. Without it, every replay after the change is a candidate lie. The lecture's rule is to add the version when the struct changes. It does not give you a particular version number to worship. It gives you the obligation to change the number, or the tag, when the layout changes, and to refuse to read a mismatch as if it matched.

The ring cares about the trivial copy, and the log cares about the version. Those are the two transports again, with the schema as the shared contract. The ring stores bytes in a slot. If the struct is not trivially copyable, that store is a data race, not a clever serializer. The log stores bytes for later. If the version is missing, the later reader guesses. Padding that is not written down is a guess about where the next field starts. Write the padding down. Fixed layout means the offsets are part of the contract, not an accident of a compiler flag you do not record. When you change a flag and the padding moves, you have changed the layout, and the version rule applies. You do not get to call it the same struct because the field names match.

Change one input: the price representation, from the teaching double to an integer tick, which is the promotion the note describes. The list of fields stays five. The meaning of the price field changes. Equality changes. The checksum test changes. The version changes. What does not change is the set of names: timestamp in nanoseconds, order id, price, quantity, side. A reader who versions only when a name is added will miss this change, and the replay will lie on a same-named field. Version the layout, not the nickname. The nickname "price" survived. The bytes did not. That is the input that matters.

You might ask whether a double is safe if you round it to a tick before you compare. Rounding at the door is a way to build an integer, and the integer is what you should have stored. If the stored form is still a double, a later reader can forget to round, and the unequal-to-itself failure returns. The note does not say "round at compare time" as the production fix. It says change price to an integer tick and update the checksum test. Store the identity you intend to compare. A side stored as a char is the same kind of choice: an explicit small set of values, not an implicit string with invisible variants. Sizes that fit are the same kind of choice. The struct is a risk control because it makes the illegal representations unrepresentable, or at least visible at the boundary where you convert.

What the claim does not mean is that the teaching file is already the production schema. The note distinguishes them. The double is in the teaching file for the benchmark. Production changes it. It does not mean a checksum you do not update will still pass and somehow be right. You update the test because the bytes changed. A passing checksum on the old layout, applied by habit to the new layout, is the replay lie in test form. It does not mean trivial copy is a performance hint. If the struct is not trivially copyable, the ring's store is a data race. That is a correctness condition. It does not mean five fields are enough for every venue. It means these five are the ones the note names. Adding a field changes the layout, so you add a version. It does not mean an implicit tick size can stay implicit once the price is an integer. The integer is the tick count. The tick size is the contract that says what that count means in price space, and it has to be explicit somewhere you version. The lecture's failure mode is an implicit tick next to a double. Moving to an integer without saying what the integer counts is a smaller version of the same hole. Write it down. Version it when it changes.

Work one equality, so the double failure is a comparison and not a slogan. Two teaching events intend the same tick. Their prices are doubles. The lecture says a double price will eventually compare unequal to itself. When that happens, a check that should deduplicate, or a join that should see one price, sees two prices. The quantity and the side can match exactly and the events still fail the price test. After you change price to an integer tick, the same intention becomes two equal integers, and the comparison holds. The timestamp in nanoseconds and the order id are still the other identity fields. They do not repair a price compare that is wrong. A version field, if you added one, matches too, or the reader should have refused the record before the compare. The schema works when unequal things are unequal and equal ticks are equal. The teaching double does not guarantee the second half. The integer tick does, for the tick you defined.

The idea in this block is idempotence. A consumer that retries must not double-apply a fill. Sequence numbers are not only a concurrency trick. They are how you know you already saw this event. The ring's ticket and the exchange's sequence are different numbers. Do not overload them.

At-least-once delivery double-applies naive handlers. Read that as arithmetic. A fill arrives. Your handler applies it. The delivery happens again, because at-least-once includes the retry. A naive handler applies it again. If the fill quantity is q, the position moves by q the first time and by q the second time. The position has moved by two q. The true fill was one q. The extra q is the double application. Nothing in the market printed a second fill. The transport printed a second delivery of the same fill. Deduplicate with an id you do not invent twice. The exchange's sequence is that kind of id, if it is stable for the event. The second delivery carries the same sequence as the first. You have seen it. You do not apply it again. The position stays at plus q, not plus two q.
